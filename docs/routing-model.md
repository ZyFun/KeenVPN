# Модель условий и порядка маршрутизации

Модуль `keenvpn.domain.routing` описывает одно условие и действие DIRECT, VPN
или BLOCK. `keenvpn.domain.routing_policy` задаёт порядок правил, обязательное
финальное действие, защищает служебный блок, исключает отключённые правила
из активного списка и выбирает первое совпадение по результатам переданного
источника. Модели работают с данными в памяти: сами не читают геобазы, не делают
DNS-запросов и не меняют конфигурацию. Выбор в модели не доказывает маршрут
реального трафика.

`keenvpn.domain.routing_explanation` выполняет [статическое объяснение](routing-explanation.md)
для явно переданных имени и IP: возвращает шаги до первого совпадения или
неизвестности, использованные метаданные геобаз и предположения о DNS/sniffing.

## Python API

Из корня исходников:

```python
from keenvpn.domain.routing import (
    DomainCondition, DomainMatch, GeoDatabase, GeoDatabaseKind,
    GeoIPCondition, GeoSiteCondition, IPCondition, RoutingAction, RoutingRule,
)

exact = RoutingRule(DomainCondition("example.test", DomainMatch.EXACT), RoutingAction.VPN)
subtree = RoutingRule(DomainCondition("пример.рф"), RoutingAction.DIRECT)
network = RoutingRule(IPCondition("192.0.2.0/24"), RoutingAction.BLOCK)

# Искусственные метаданные. Их передача не проверяет файл или его содержимое.
ip_database = GeoDatabase(GeoDatabaseKind.GEOIP, "ip-test", version="test-release")
site_database = GeoDatabase(
    GeoDatabaseKind.GEOSITE,
    reference="sites-test",
    source="https://data.example.test/sets",
    version="test-release",
    sha256="ab" * 32,
)
country = RoutingRule(GeoIPCondition(ip_database, "ru"), RoutingAction.DIRECT)
sites = RoutingRule(GeoSiteCondition(site_database, "test-set"), RoutingAction.VPN)

assert subtree.condition.value == "xn--e1afmkfd.xn--p1ai"
assert subtree.condition.display_name == "пример.рф"
assert country.condition != sites.condition
```

Все модели неизменяемые. Для действия, режима домена, типа базы и семейства
неизвестного условия используются соответствующие Enum; обычная строка вместо
Enum отклоняется. Действие обязательно, автоматического DIRECT при ошибке нет.
VPN обозначает направление, не выбирает профиль и не проверяет его доступность.
`RoutingRule` принимает именованные параметры `enabled=True` и `protected=False`.
Оба требуют именно `bool`: строки и числа `0`/`1` не преобразуются автоматически.
Это метаданные модели, а не поля Xray JSON. Условия и действия проверяются также
для отключённого правила.

## Условия

| Модель | Значение и ограничения |
| --- | --- |
| `DomainCondition(value, mode)` | `EXACT` — точное имя; `SUBDOMAINS` — имя и его поддомены, режим по умолчанию. |
| `IPCondition(value)` | IPv4/IPv6-адрес либо CIDR с числовой длиной префикса. |
| `GeoIPCondition(database, set_name)` | Набор IP в базе типа `GEOIP`. |
| `GeoSiteCondition(database, set_name)` | Доменный набор в базе типа `GEOSITE`. |
| `UnknownCondition(family, reference)` | Неподдержанная импортированная ссылка в исходном виде. |

Точный домен и домен с поддоменами — разные условия даже при одинаковом имени.
Режимы соответствуют смыслу `full:` и `domain:` в [документации Xray](https://xtls.github.io/en/config/routing.html#ruleobject).
В модель передаётся имя **без** этих префиксов. Сопоставления с конкретным
доменом или IP и преобразования в Xray JSON в этом модуле нет.

Домены приводятся к нижнему регистру, Unicode NFC и ASCII IDNA; одна конечная
точка DNS удаляется. Unicode-разделители `。`, `．`, `｡` принимаются как точки.
`display_name` возвращает Unicode-представление для явного показа пользователю.
Пустые метки, пробелы, URL, IP вместо домена, порты, wildcard, префиксы правил и
некорректный Punycode отклоняются. Длина ASCII-метки ограничена 63 символами,
имени без конечной точки — 253.

Используется IDNA стандартной библиотеки Python, с проверкой обратного
преобразования. Преобразования с потерей исходного имени отклоняются: например,
`faß.test` не заменяется на `fass.test`, невидимые символы не удаляются.
Это ограниченное множество IDNA-имён, а не полная поддержка IDNA2008/UTS #46.

IP приводится к стандартной форме `ipaddress`. Адрес и явно заданная сеть
`/32` или `/128` сохраняют различие. CIDR с битами хоста, например
`192.0.2.1/24`, отклоняется, а не расширяется до `192.0.2.0/24`. Маски в форме
`255.255.255.0`, зональные IPv6-адреса с `%`, порты и имена вместо IP не принимаются.

`DomainCondition("ru")`, `DomainCondition("su")` и `DomainCondition("рф")`
представляют доменные зоны с поддоменами; последняя хранится как `xn--p1ai`.
Они независимы от страны GeoIP и категории GeoSite. Создание или описание базы
не создаёт таких правил автоматически.

## Метаданные геобаз

`GeoDatabase` хранит тип, обязательную непрозрачную ссылку `reference`, источник
`source`, версию `version` и `sha256`. Последние три поля могут быть `None`:
это неизвестные сведения. Пустая строка вместо известного значения недопустима.
Версия не извлекается из имени файла. SHA-256 проверяется только по формату
64 шестнадцатеричных символов и приводится к нижнему регистру.

`reference` не открывается как файл, `source` не загружается. Имя набора
сохраняется с исходным регистром. Допускаются ASCII-буквы, цифры, `_`, `-`, `.`,
`!`, `@`; первый символ — буква или цифра. Это проверка формы имени, а не его
наличия в каталоге. Тип базы должен соответствовать типу условия.

Даже полностью заполненные метаданные **не подтверждают** наличие, целостность,
подлинность или совместимость базы, существование набора и принадлежность ему
домена/IP. Модель не предоставляет разрешения на применение правила.

## Неизвестные импортированные ссылки

```python
from keenvpn.domain.routing import ConditionFamily, RoutingAction, RoutingRule, UnknownCondition

original = "ext:Custom-test.dat:Unknown@attribute"
condition = UnknownCondition(ConditionFamily.DOMAIN, original)
rule = RoutingRule(condition, RoutingAction.VPN)
assert rule.condition.reference == original
assert rule.read_only is True
```

Это контейнер для импортирующего кода, не импортёр действующих конфигураций.
Он сохраняет непустую строку посимвольно, включая неподдержанный синтаксис,
регистр, пробелы и управляющие символы, а также исходное семейство DOMAIN/IP.
Ссылка не разбирается, не исполняется, не заменяется доменом, категорией или
известной базой. `RoutingRule.read_only` всегда истинен для такого условия.
Для известных условий ложное значение означает только поддержанный тип;
оно не свидетельствует о проверке базы или готовности применения.

## Порядок правил и финальное действие

`RoutingPolicy(rules, final_rule)` принимает tuple или список обычных
`RoutingRule` (служебных и пользовательских) и обязательный `FinalRoutingRule(action)`. Переданный список
копируется в tuple. Порядок и повторения сохраняются; сортировки по типу
условия, действию или специфичности домена нет. `ordered_rules` возвращает
обычные правила и ровно одно финальное последним. Финальное правило нельзя
поместить в `rules`; отсутствие финального действия и строка вместо
`RoutingAction` отклоняются. Даже пустой набор обычных правил требует явно
выбранного финального действия.

Все операции возвращают новую модель; исходная остаётся неизменной:

| Операция | Поведение |
| --- | --- |
| `insert(index, rule)` | Вставляет пользовательское правило перед индексом `protected_rule_count..len(rules)`. Последняя допустимая позиция — перед финальным. |
| `move(source_index, target_index)` | Перемещает пользовательское правило на итоговый индекс после служебного блока, сохраняя взаимный порядок остальных. |
| `remove(index)` | Удаляет только пользовательское правило. Служебные и финальное сохраняются. |
| `with_final_action(action)` | Явно меняет финальное действие, сохраняя порядок условий. |
| `with_enabled(index, enabled)` | Включает или выключает пользовательское правило, сохраняя условие, действие и позицию. |

Индексы начинаются с нуля и относятся к конкретной версии модели. Отрицательные
индексы, `bool`, дробные числа и выход за границы не принимаются. Финальное
правило нельзя удалить, переместить или добавить обычное правило после него.
Эти операции меняют только данные в памяти и не применяют конфигурацию.

Если есть хотя бы одно `UnknownCondition`, даже в отключённом правиле,
`RoutingPolicy.read_only` истинен и все пять операций отклоняются с `READ_ONLY`. Это сохраняет также
относительный приоритет неизвестного условия, который мог бы измениться при
перемещении соседнего правила. Просмотр, получение полного порядка и выбор
по результатам известного префикса доступны. Прямое создание другой модели
не является разрешением на редактирование или применение импортированной
конфигурации.

## Служебные и отключённые правила

Служебное правило обозначается `protected=True` при создании модели. Оно
обязательно включено. В `RoutingPolicy` все служебные правила образуют
непрерывный блок в начале; пользовательские следуют за ним, финальное — в конце.
Неправильный порядок отклоняется без автоматической сортировки.

Операции политики защищают этот блок:

- `remove`, `move` и `with_enabled` не принимают индекс служебного правила,
  включая попытку оставить его на месте или повторно включить.
- `insert` и `move` не позволяют поставить пользовательское правило перед
  служебным или между служебными, даже если пользовательское отключено.
- `insert` принимает только пользовательские правила; добавить служебное
  через эту операцию нельзя. `protected_rule_count` даёт первый допустимый
  индекс вставки пользовательского правила.
- Пользовательские правила можно редактировать после служебного блока;
  `with_final_action` сохраняет служебные правила и их взаимный порядок.

Признак `protected` задаёт вызывающий код, не автоматическое распознавание DNS
или локальной сети. Модель не создаёт системных исключений. Публичный конструктор
предназначен для доверенного кода: создание другой модели или `dataclasses.replace`
не являются защищённым редактором и не дают разрешения на применение конфигурации.
`read_only` обозначает неизвестное условие; защита известных служебных правил
проверяется отдельно и не блокирует весь пользовательский раздел.

`rules` и `ordered_rules` сохраняют отключённые правила вместе с их позициями.
`active_rules` возвращает отдельный tuple только включённых правил и финального,
в исходном порядке. Отключённые условия не передаются в `matcher` и не участвуют
в выборе действия. Включение возвращает правило в сохранённую позицию; явное
перемещение отключённого правила меняет эту позицию. Все индексы операций и
`RoutingSelection.index` относятся к сохранённому списку, а не к `active_rules`.
Финальное правило выключить нельзя.

```python
from keenvpn.domain.routing import DomainCondition, IPCondition, RoutingAction, RoutingRule
from keenvpn.domain.routing_policy import FinalRoutingRule, MatchResult, RoutingPolicy

# Искусственное условие для демонстрации защиты, не готовое сетевое исключение.
service = RoutingRule(IPCondition("192.0.2.0/24"), RoutingAction.DIRECT, protected=True)
custom = RoutingRule(DomainCondition("example.test"), RoutingAction.VPN)
policy = RoutingPolicy((service, custom), FinalRoutingRule(RoutingAction.BLOCK))
disabled = policy.with_enabled(1, False)

assert disabled.rules[1].condition is custom.condition
assert disabled.ordered_rules == (service, disabled.rules[1], policy.final_rule)
assert disabled.active_rules == (service, policy.final_rule)
assert disabled.with_enabled(1, True) == policy

selection = disabled.select_first(lambda _: MatchResult.NO_MATCH)
assert selection.is_final is True
assert selection.index == 2  # Индекс в ordered_rules; в active_rules он равен 1.
assert policy.rules[1].enabled is True  # Исходная модель не меняется.
```

Активный список содержит доменные объекты в памяти; это не сериализатор и
не действующий `routing.rules` Xray. Отключённые данные остаются в модели,
файлы метаданных и резервные копии этот API не записывает. Неизвестное включённое
условие сохраняется в `active_rules`, но останавливает выбор, если обход до него
дошёл. Получение списка не проверяет применимость конфигурации или геобаз.

## Выбор первого совпадения

`select_first(matcher)` обходит включённые правила сверху вниз. Переданная
функция получает условие и возвращает строго один из `MatchResult`:

- `MATCH` — вернуть это правило и остановиться; более поздние не проверяются.
- `NO_MATCH` — перейти к следующему правилу.
- `UNKNOWN` — остановиться с ошибкой `MATCH_UNKNOWN`, без выбранного действия.

Финальное правило выбирается, только когда все включённые правила вернули
`NO_MATCH` (либо включённых нет); источник для отключённых и финального правила не вызывается. Если обход дошёл
до `UnknownCondition`, выбор останавливается с `MATCH_UNKNOWN` без вызова
источника для этого условия. Неизвестное правило после уже найденного
совпадения на результат не влияет.

Тот же порядок обхода доступен как `walk_first_match(evaluate, skip=None)`:
`evaluate(index, rule)` вызывается для включённых правил и возвращает
`MatchResult`, `skip(index, rule)` — для отключённых. Метод возвращает
`RoutingSelection` либо `None` при первом `UNKNOWN`, без ошибки. На нём построены
`select_first` и [статическое объяснение](routing-explanation.md).

```python
from keenvpn.domain.routing import (
    DomainCondition, GeoDatabase, GeoDatabaseKind, GeoIPCondition,
    RoutingAction, RoutingRule,
)
from keenvpn.domain.routing_policy import FinalRoutingRule, MatchResult, RoutingPolicy

country = RoutingRule(
    GeoIPCondition(GeoDatabase(GeoDatabaseKind.GEOIP, "ip-test"), "ru"),
    RoutingAction.DIRECT,
)
exception = RoutingRule(DomainCondition("example.test"), RoutingAction.VPN)
policy = RoutingPolicy((country, exception), FinalRoutingRule(RoutingAction.BLOCK))

# Искусственный источник: считаем оба условия совпавшими для одного запроса.
# Это пример приоритета, а не определение страны или реального маршрута.
def known_match(condition):
    return MatchResult.MATCH

assert policy.select_first(known_match).action is RoutingAction.DIRECT
changed = policy.move(1, 0)
selection = changed.select_first(known_match)
assert selection.rule is exception
assert selection.index == 0
assert selection.action is RoutingAction.VPN
assert selection.is_final is False
assert changed.ordered_rules[-1] is policy.final_rule
assert policy.rules == (country, exception)

remainder = changed.select_first(lambda condition: MatchResult.NO_MATCH)
assert remainder.is_final is True
assert remainder.action is RoutingAction.BLOCK
```

Результат — неизменяемый `RoutingSelection(index, rule)` со свойствами
`action` и `is_final`. Он относится к конкретной модели и результатам
источника, не подтверждает доступность VPN или применимость Xray-конфигурации.

Порядок соответствует принципу первого совпадения в
[документации Xray](https://xtls.github.io/en/config/routing.html#routingobject).
Модель требует явного финального действия. В Xray при отсутствии совпадений
выбирается первый outbound; модель не полагается на этот неявный выбор
и не генерирует Xray JSON.

`matcher` — доверенная функция для одного фиксированного сценария. Модель
не реализует сопоставление домена/IP, DNS, sniffing или чтение наборов геобаз
и не проверяет достоверность переданных результатов. Наличие метаданных базы
само по себе не даёт `MATCH` или `NO_MATCH`. Модель не изолирует функцию от
ввода/вывода: отсутствие побочных эффектов зависит также от её реализации.

## Ошибки и безопасный вывод

Некорректные значения вызывают `RoutingValidationError` с `code` из
`RoutingErrorCode`. Например, CIDR с битами хоста возвращает `IP`, а перепутанные
GeoIP/GeoSite — `DATABASE_KIND`. Ошибка не включает исходный ввод и не
подменяется правилом с другим действием. В стандартном traceback подавляется
вывод контекста внешнего исключения, внутри обработчика которого вызвана модель.
Сам объект внешнего контекста не очищается и не предназначен для диагностики.

Для порядка используются коды `RULES`, `FINAL_RULE`, `POSITION`, `READ_ONLY`.
Для состояния — `RULE_STATE`; для попытки изменить служебное правило или
создать его отключённым — `PROTECTED_RULE`; для нарушения служебного блока —
`PROTECTED_ORDER`. Эти отказы содержат безопасное объяснение на русском языке.
Некорректный результат источника, включая `True`, `False` или `None`, вызывает
`MATCH_RESULT`. Отсутствующий/невызываемый источник или его исключение вызывает
`MATCHER`. При преобразовании исключения источника у новой ошибки явно очищается
`__context__`, а `__cause__` остаётся `None`: исходное исключение, его цепочка и
кадры traceback не удерживаются через цепочку новой ошибки. Это действует также
при вызове внутри внешнего `except`. Собственный traceback новой ошибки всё ещё
содержит кадры вызывающего кода и модели; захват их локальных переменных небезопасен.
`KeyboardInterrupt` и `SystemExit` не перехватываются. Ни один отказ не подменяется финальным
действием или DIRECT. `MATCH_UNKNOWN` означает недостаток сведений для выбора,
а не применение BLOCK к реальному трафику.

`repr()`/`str()` моделей с произвольными полями скрывают эти поля. `RoutingRule.to_diagnostic()`
содержит только тип условия, действие, признаки `read_only`, `enabled`, `protected` и отметку скрытых
параметров. Для `FinalRoutingRule` выводится только проверенный Enum действия.
`RoutingPolicy.to_diagnostic()` содержит число сохранённых, включённых и служебных
правил (каждое без финального), финальное действие и `read_only`;
`RoutingSelection.to_diagnostic()` — индекс, действие
и `is_final`. Поля модели, `display_name`, `dataclasses.asdict()`, дампы памяти
и traceback с захватом локальных переменных **не являются безопасным выводом**.
Не журналируйте их: произвольная ссылка или источник могут содержать секрет,
а исходная неизвестная строка — управляющие символы.

## Локальные проверки

```sh
python3 -I -S -B -m unittest discover -s tests -p 'test_routing*.py' -v
```

Тесты используют искусственные имена, адреса и метаданные. Они проверяют
валидацию, независимость условий, неизменяемость, сохранение неизвестных
ссылок, порядок, защиту служебного блока, отключение и повторное включение,
отдельный активный список, закрепление финального правила, остановку выбора на совпадении,
неизвестности и ошибке, безопасный обычный вывод. С управляемым чистым источником
проверяется отсутствие файловых, сетевых и процессных операций. Это не проверка
Xray, геобаз или реального сетевого маршрута.
