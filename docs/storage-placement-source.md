# Чтение размещения хранилищ

`keenvpn.adapters.storage_placement_files.StoragePlacementFiles` реализует
`StoragePlacementSource.current_storage_placement() -> StoragePlacement`
для существующего [первичного импорта](manager-metadata.md#прикладные-сценарии).
Источник работает на Keenetic KN-1811 с Entware в `/opt`: читает файлы,
mountinfo и UUID BusyBox `blkid`. SQLite, архив, writer и init не запускаются,
каталоги и файлы не создаются. `vpn-menu --read-router` и `vpn-setup` используют
источник для [подключения хранилищ чтения](cli-menu.md#хранилища-на-роутере) по DATA.

Просмотр из Python без записи:

```python
from keenvpn.adapters.storage_placement_files import StoragePlacementFiles
from keenvpn.domain.manager_metadata import ManagerMetadata

placement = StoragePlacementFiles().current_storage_placement()
view = ManagerMetadata(placement).to_diagnostic()
```

Значения `storage_id.value` и `path.value` предназначены для доверенного кода;
не выводите их. Безопасное представление и `repr` моделей скрывают UUID и пути.

## Форматы

| Данные | Источник |
| --- | --- |
| DATA и копии | `/opt/etc/vpn-backup.json`: ровно `entware_uuid`, `data_uuid`, `backup_uuid`, `keep`; UUID различаются, `keep` — целое 1–30 |
| Формат размещения архива | Известные тексты `/opt/sbin/vpn-backup`, `/opt/share/keenvpn-backup/scripts/router_backup.py` и `keenvpn/adapters/router_backup.py` внутри того же установленного каталога |
| История | Литералы `history_uuid`, `history_mount`, `history_store` в `/opt/sbin/vpn-history` и известный `/opt/etc/init.d/S07vpn-history` |
| Бюджет истории | Проверка `history_size` в writer, КиБ переводятся в байты |
| Срок истории | Три одинаковых срока очистки `cycles`, `events`, `internet_cycles` в `/opt/etc/vpn-history/ingest.sql`, в секундах |
| Идентичность | `/proc/<PID текущего процесса>/mountinfo`, полная строка `blkid` и `.store-id` каталога истории |

Для архиватора поддерживается одна побайтная версия файлов, совпадающая с
`scripts/router_backup.py` и `keenvpn/adapters/router_backup.py` в этой поставке.
Её отпечатки закреплены в `BACKUP_ENTRY_SHA256` и `BACKUP_ADAPTER_SHA256`.
Даже изменение docstring меняет отпечаток. Обновление этих файлов требует
согласованной проверки поддерживаемых эталонов источника; отдельный тест
проверяет эту связь и поясняет причину расхождения. Иные установленные версии,
не совпадающие побайтно, отклоняются с `invalid_response`, включая ранее
развёрнутую копию, если её отпечаток больше не входит в поддерживаемый формат.

У поддерживаемого архива DATA — корень `/tmp/mnt/<UUID>`, копии — каталог
другого выбранного раздела `keenvpn/daily`. Три явно заданных разных UUID
означают расширенный вариант. Без такого свидетельства вариант неизвестен:
число подключённых разделов не доказывает простой вариант.

Структура shell/SQL фиксирована. Разрешены изменяемые литералы UUID, mount,
каталога, бюджета и запаса места в shell, согласованного срока, предела страниц
и порога очистки в SQL. Остальной текст после замены литералов сверяется по
SHA-256 с обезличенной эталонной структурой. Пути — нормализованные абсолютные
ASCII-литералы без пробелов и shell-подстановок. Дубли, неизвестная структура,
неполные файлы, повреждённый JSON и разные сроки дают отказ целиком. Прочитанные
shell и SQL не исполняются. Новые defaults не выбираются.

Для истории поддерживаются две согласованные пары writer/SQL: v3 с двумя
ключами проб `primary` и `backup` и v4 с третьим ключом `hysteria`.
В v4 назначение ID 1/2/3 задано явно, без запасной ветви `ELSE`; writer
требует `user_version=4` вместо `3`. В обоих форматах сохраняется требование
`journal_mode=delete`. Это проверка текстов, а не чтение PRAGMA из базы.
Смешанные пары v3/v4 и остальные изменения структуры отклоняются целиком с
`invalid_response`. Источник не мигрирует SQLite и не изменяет скрипты истории.

`size_bytes` — общий бюджет истории с журналами, не предел файла БД или размер
раздела. Текущие PRAGMA и содержимое SQLite не читаются. Источник не проверяет
исправность БД, фактический расход или достаточность свободного места.

## Проверка и неполнота

Настроенные UUID/путь сохраняются с `verified=False`, если размещение недоступно.
Подтверждение требует единственного наиболее вложенного mount для пути,
ext4 с корнем `/`, `rw` в обоих наборах флагов, совпадения UUID и номера
block-device, принадлежности каталога этой файловой системе и отсутствия
вложенных mount внутри каталога роли. Истории нужен совпадающий `.store-id`;
формату архива — дополнительно bind `/opt` на выбранном ENTWARE.
При сравнении маркера отбрасываются только конечные `LF`, как у writer:
пустой или отсутствующий маркер, пробелы, `CR` и лишний текст не подтверждают историю.

Отсутствующий mount не позволяет проверять нижележащий каталог RAM. Подменённый
номер или UUID, одинаковые UUID разных устройств, read-only, bind подкаталога и
неоднозначная точка mount не подтверждаются. Первый кандидат не выбирается.
Компоненты путей открываются с `O_NOFOLLOW`; ссылка — отказ `unsafe`.
Источник ничего не монтирует и не переключает на другой носитель.
У служебного `nsfs` парсер допускает root вида `net:[12345]`, который не является
файловым путём. Такая строка не подтверждает хранилище; mount внутри каталога
роли по-прежнему снимает подтверждение. Для ext4 требование корня `/` сохраняется.

Нет одновременно конфигурации и wrapper архива — обнаруженная роль копий
`absent`, DATA `unknown`: отсутствие архива не доказывает отсутствие данных.
Нет одновременно writer и init истории — обнаруженная история и оба лимита
`absent`. Неполная пара — отказ. Эти состояния относятся к поддерживаемым
операционным источникам, произвольные другие системы не обнаруживаются.

В конце сравниваются повторно прочитанные файлы, номера и UUID устройств, идентичности
проверенных каталогов и mountinfo. Обнаруженное изменение — `changed`.
Это последовательные наблюдения, не блокировка внешнего администратора после
последней проверки. Отказы — `RouterReadError` с фиксированным кодом без путей,
содержимого, потоков команд и цепочек системных исключений.

## Пределы и локальная проверка

Mountinfo — 128 КиБ и 1024 записи, USB-устройств — до восьми. JSON и wrapper
архива — по 4 КиБ, init истории — 16 КиБ, остальные тексты — по 128 КиБ,
маркер — 128 байт. `blkid` вызывается массивом аргументов без shell, с пустым
окружением, закрытым stdin, сроком 5 секунд и пределом stdout 32 КиБ;
stderr отбрасывается. Ненулевой код — `exit_status`, превышение размера —
`too_large`, срока — `timeout`. Два обхода восьми устройств допускают до
80 секунд ожидания команд, если все завершаются у своего срока.

Конструктор принимает `root` (по умолчанию `/`, иной — для тестов) и `run`
существующего типа `CommandRunner`. Создание ничего не читает; каждый вызов
собирает новую модель.

```sh
python3.12 -I -S -B -m unittest discover -s tests -p test_storage_placement_files.py -v
```

Тесты используют отдельные обезличенные тексты и временные каталоги. Обход
путей настоящий, номера устройств контролируются тестовым источником.
Проверки форматов, mount/UUID, отказов и повторного импорта не подтверждают
аппаратные отказы USB, работоспособность VPN или состояние SQLite.
