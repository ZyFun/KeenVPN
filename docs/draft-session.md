# Сессия черновика

Модуль `keenvpn.domain.draft_session` описывает одну редактируемую сессию черновика изменений: идентификатор, время создания, сохранённый кандидат и [исходные отпечатки](#исходные-отпечатки) управляемых источников в строгом версионированном формате. Он разбирает и собирает байты файла в памяти и ничего не читает с диска. Адаптер `keenvpn.adapters.draft_session_files.DraftSessionFiles` хранит файл сессии в явно заданном собственном каталоге; порт `DraftSessionStore` и его отказы определены в `keenvpn.application.ports`. Над портом работают [прикладные сценарии](#прикладные-сценарии) создания, редактирования, просмотра, проверки актуальности и отмены.

Черновик ничего не применяет: адаптер и сценарии не меняют конфигурацию Xray и XKeen, настройки Keenetic и службы, не вызывают команды XKeen и не меняют роутер. Создание и проверка актуальности только читают отпечатки источников, их содержимое не разбирается. Файл сессии не размещается в каталогах конфигураций Xray и XKeen и каталоге init, поэтому Xray не может загрузить его как свою часть. Необязательный раздел `candidate` хранит полные исходный и изменённый снимки; наличие файла означает открытую сессию. Сборка меню принимает хранилище через `MenuSources(drafts=...)`. Режимы `vpn-menu --read-router` и `vpn-setup` выбирают собственный каталог по подтверждённой роли `data` и подключают его только для [чтения](cli-menu.md#хранилища-на-роутере). `vpn-menu` без флага источников не подключает. Пункты 7 → 1 и 7 → 2 читают сохранённый кандидат для diff и проверки через [общие сценарии](#проверки-сохранённого-кандидата). Подключённое хранилище читают область «Черновик» [сводки](status-summary.md) и [решение о выходе](cli-menu.md#выход-при-неприменённом-черновике) из меню; оба только читают файл.

## Проверки сохранённого кандидата

`keenvpn.application.saved_draft` связывает файл сессии с существующими
сценариями. Команды `CompareSavedDraft` и `CheckSavedDraft` принимают
`draft_id`, `expected_revision` из `DraftView` и `contract_version=1`.
Хранилище и текущие отпечатки обязательны; результат не содержит приватных
снимков, ID, токена или SHA. Сессия и активные источники не записываются.

- `CompareSavedDraftHandler(store, fingerprints)` передаёт оба полных снимка
  сохранённого `candidate` в `CompareDraftHandler`. Действуют его проверка
  original по baseline, лексический порядок original Xray, значимый порядок
  candidate, предел отчёта и различение неверного original, конфликта
  источников и конфликта сессии. Результат — прежний `DraftDiffView`.
- `CheckSavedDraftHandler(store, fingerprints, geodata=None, assets=None,
  catalogs=None, tester=None)` сначала сравнивает original с самим собой
  общим `CompareDraft`, чтобы проверить полноту и связь с baseline без
  построения списка изменений. Из одного сохранённого снимка и ожиданий
  собираются входы `CheckDraftCandidate` и `CheckInstalledXray`. Общий
  `CheckDraftBaseline` дополнительно сверяет актуальность между проверками
  и перед итогом; обнаруженный конфликт отменяет весь отчёт.

`SavedDraftCheckView` содержит отдельные поля `static`/`static_error` и
`binary`/`binary_error`. Успех операции чтения этого представления не
означает успех обеих проверок. Ошибки доступны как `ErrorDetail` со следующим
шагом; успешные чтения — `DraftCandidateView` и `CheckView`. Статическая
ошибка или неполнота не подменяет фактический исход бинарной проверки.

`GeoCategorySource.read_catalogs(revisions)` — доверенный порт сборки;
каталоги не берутся из файла сессии или пользовательского ввода. Сам
`CheckDraftCandidate` проверяет точный вид, имя, SHA и содержимое свидетельства.
В штатной сборке поставщика каталогов нет: отсутствие свидетельства даёт
честную неполноту. `CandidateAssetSource.read_asset(name, limit)` возвращает
полные байты зависимостей. Встроенный `GeoCandidateFiles` читает их из
каталога геобаз без ссылок и с контролем подмены. Ожидаемые SHA всегда
берутся из сессии; несовпавшие байты не принимаются под новым хешем. Ненужные
ожидания файлов не добавляются в бинарный вход. Перечень зависимостей
вычисляет общий `candidate_geo_references`, который использует и
`CheckInstalledXray`.

| Состояние | Результат |
| --- | --- |
| В сессии нет `candidate` | `draft_candidate_missing`; прежняя v1 остаётся без изменений |
| Неполный или повреждённый сохранённый снимок | Отказ чтения `invalid_stored_draft`; частичный diff не строится |
| Xray/init/списки портов не позволяют собрать статический вход | `static_error` / `draft_check_input_unavailable` |
| Доверенный поставщик каталогов отказал | `static_error` / `draft_catalogs_unavailable` |
| Источник байтов геобаз отсутствует, отказал или вернул неверный тип/размер | `binary_error` / `draft_assets_unavailable` |
| Нет ожидаемой ревизии зависимого файла | Бинарная `not_checked` / `geo_revision_unknown`, без чтения байтов |
| Xray явно отсутствует в снимке | Бинарная `not_checked` / `candidate_xray_absent` |
| Каталог Xray присутствует, но частей нет | Бинарная `not_checked` / `candidate_xray_empty`, без чтения байтов геобаз и запуска |
| Допустимый сохранённый кандидат не проходит более строгий контракт бинарного входа, например предел структуры JSON | Бинарная `not_checked` / `candidate_binary_input_unsupported`; статический результат сохранён, исполнитель не запущен |
| Исполнитель не подключён | При полных допустимых входах `xray_test_unavailable` / `xray_isolation_unavailable` |

Пределы чтения и исполнения различны: файлы геобаз загружаются в память
координатора, до 256 МиБ каждый и 512 МиБ суммарно. Предел 256 МиБ
проверочного Xray и его потомков не ограничивает память координатора.
Повторные проверки размещения DATA и чтения источников происходят вне
30-секундного срока исполнителя. Проверка не блокирует внешние изменения
после последнего чтения; результат не является разрешением на применение.

## Формат

Файл — объект JSON версии схемы `1`:

```json
{
  "format": "keenvpn-draft-session",
  "schema_version": 1,
  "draft_id": "00000000-0000-4000-8000-0000000000d1",
  "created_at": "2026-11-01T02:14:16Z",
  "baseline": {
    "xray_configs": {"state": "present", "parts": {"01_log.json": "<SHA-256>", "02_dns.json": "<SHA-256>"}},
    "xkeen_settings": {"state": "present", "sha256": "<SHA-256>"},
    "xkeen_init": {"state": "absent"}
  }
}
```

В примере раздел `baseline` сокращён: созданный сценарием черновик содержит все источники перечня.

| Поле | Значение |
|---|---|
| `format` | Строка `keenvpn-draft-session`; без неё файл не считается черновиком, в том числе файл [метаданных менеджера](manager-metadata.md) |
| `schema_version` | Целое `1`; другая версия не угадывается и не мигрирует |
| `draft_id` | UUID `8-4-4-4-12` в нижнем регистре, выданный при создании; регистр не нормализуется |
| `created_at` | Момент создания в UTC с точностью до секунды: `YYYY-MM-DDTHH:MM:SSZ`, год из четырёх цифр; несуществующие дата и время отклоняются |
| `baseline` | Необязательный раздел [исходных отпечатков](#исходные-отпечатки); черновик без него остаётся допустимым файлом версии 1 |
| `candidate` | Необязательный приватный [раздел кандидата](#сохранённый-кандидат); отсутствие означает, что кандидат ещё не сохранён, а `null` недопустим |

Модель — `DraftSession(draft_id, created_at, extra, baseline=None, candidate=None)`: `created_at` — `datetime` с `tzinfo=timezone.utc` без долей секунды, `extra` — [`UnknownFields`](manager-metadata.md#неизвестные-поля), `baseline` — `SourceBaseline` либо `None`, `candidate` — `DraftCandidateState` либо `None`. Конструктор требует точных типов: подкласс `str` или `datetime`, наивное время и другой часовой пояс не проходят.

Поля, неизвестные этой версии формата, сохраняются на верхнем уровне так же, как в метаданных менеджера: каноническим JSON-снимком, после известных полей в исходном порядке; поле с именем известного задать нельзя. Будущие разделы формата добавляются как необязательные поля верхнего уровня.

## Строгое чтение и ревизия

`decode_draft_session(content)` принимает байты и возвращает `StoredDraftSession(session, revision)`. Отклоняются:

- не байты, не UTF-8 и файл больше `MAX_DRAFT_SIZE` (1 МиБ) — `invalid_draft_content`;
- комментарии, дубли ключей, `NaN`, `Infinity`, BOM, вложенность глубже 64 и не объект верхнего уровня — `invalid_draft_json`;
- неверный маркер формата, версия не целое положительное число, отсутствие `draft_id` или `created_at` — `invalid_draft_format`;
- другая версия схемы — `unsupported_draft_schema_version`, остальные поля не разбираются;
- `draft_id` и `created_at` неверного формата — `invalid_draft_id` и `invalid_draft_created_at`;
- раздел `baseline`, нарушающий [строгий разбор](#исходные-отпечатки), в том числе `null`, — `invalid_draft_baseline`;
- повреждённый или неполный раздел `candidate` — `invalid_draft_candidate`.

Ревизия — SHA-256 байтов файла (`draft_revision`), как у метаданных менеджера. `encode_draft_session(session)` заново проверяет модель и возвращает ASCII-текст с отступом и переводом строки в конце; повторное кодирование прочитанного канонического файла даёт те же байты. `validate_draft_session(session)` пересобирает модель из её собственных полей и неизвестные поля из их снимка.

`DraftSessionError` содержит `code` (`DraftSessionErrorCode`) и `field` — имя поля формата либо `None`; значения и имена неизвестных полей в ошибку не попадают, чужое исключение в `__context__` не сохраняется. Коды: `invalid_draft_content`, `invalid_draft_json`, `invalid_draft_format`, `unsupported_draft_schema_version`, `invalid_draft_id`, `invalid_draft_created_at`, `invalid_unknown_fields`, `invalid_draft_baseline`, `invalid_draft_candidate`, `invalid_draft_revision`, `invalid_draft_session`.

`DraftSession.to_diagnostic()` возвращает версию схемы, идентификатор, время создания строкой, число неизвестных полей и `baseline` — источники с состояниями либо `None`; `repr` показывает идентификатор, время, только число неизвестных полей и число источников, без хешей.

## Исходные отпечатки

При создании черновика сценарий фиксирует, в каком состоянии были источники, которыми управляет менеджер. Модуль `keenvpn.domain.source_baseline` описывает перечень источников, модель отпечатка и раздел `baseline`; порт `SourceFingerprintSource` определён в `keenvpn.application.ports`, его реализация на роутере — [`SourceFingerprints`](router-sources.md#исходные-отпечатки).

| Источник `BaselineSource` | Что фиксируется |
|---|---|
| `xray_configs` | Набор имён `*.json` каталога конфигураций Xray и SHA-256 байтов каждой части по порядку имён; служебные части входят наравне с остальными |
| `xkeen_settings` | SHA-256 байтов `xkeen.json` |
| `xkeen_init` | SHA-256 байтов стартового сценария XKeen |
| `xkeen_port_exclude`, `xkeen_port_proxying`, `xkeen_ip_exclude` | SHA-256 байтов каждого из трёх списков |
| `keenetic_policies` | SHA-256 канонического JSON всего ресурса RCI `ip/policy`, включая разрешённые подключения политик |
| `keenetic_hotspot_settings` | SHA-256 канонического JSON всего ресурса RCI `ip/hotspot` |

Геобазы, реестр регистраций `known/host`, наблюдаемое состояние клиентов `show/ip/hotspot` и процесс Xray не фиксируются. Порядок перечня — порядок чтения и записи.

Канонический JSON (`native_fingerprint`) — ключи объектов по порядку, массивы в исходном порядке, без пробелов, в ASCII. Перестановка ключей отпечаток не меняет, а перестановка разрешённых подключений, замена `true` на `1`, новое или удалённое поле — меняют. В ресурсах `ip/policy` и `ip/hotspot` нет счётчиков, поэтому значим весь объект, включая неизвестные менеджеру поля.

Отпечаток `SourceFingerprint(source, state, sha256=None, parts=None)` имеет состояние `present` или `absent`. Подтверждённое отсутствие файла, каталога или его родителя — `absent` без хешей; отсутствие, замеченное в каталоге, который во время чтения заменён по пути, — отказ чтения `changed`. Пустой файл — `present` с SHA-256 пустых байтов, пустой каталог частей — `present` с пустым набором `parts`. Новая, удалённая или переименованная часть Xray меняет набор. Источник, который прочитать не удалось, отпечатка не получает: порт передаёт отказ чтения, и черновик не создаётся.

Разбор раздела строгий (`parse_source_baseline`):

- у записи известного источника ровно поля своего состояния: `state` и `sha256`, у `xray_configs` — `state` и `parts`, у `absent` — только `state`;
- состояние — `present` или `absent`, другое значение отклоняется;
- SHA-256 — 64 шестнадцатеричные цифры в нижнем регистре;
- имя части — допустимое имя файла без каталога с окончанием `.json`, не скрытое, частей не больше 64;
- порядок ключей не значим: источники упорядочиваются по перечню, части — по имени.

Записи источников, неизвестных этой версии, сохраняются без изменений после известных: сравнить их эта версия не может, поэтому проверка актуальности такой черновик блокирует. Раздел может перечислять не все источники; сценарий создания всегда записывает все. Неизвестная запись, которую строгий разбор файла не прочитал бы из-за глубины вложенности, не записывается: `invalid_draft_baseline`.

Хеши и имена частей не попадают в `repr`, диагностику, представления сценариев и ошибки: по хешу файла с малой изменчивостью можно проверить догадку о его содержимом. `SourceBaseline.to_diagnostic()` возвращает источники с состояниями и число неизвестных записей. `rebuild_source_baseline(baseline)` и `validate_source_fingerprint(fingerprint)` заново проверяют готовые модели из точных типов. `same_fingerprint(first, second)` сравнивает два отпечатка: тот же источник, то же состояние и те же хеши, у каталога частей Xray — тот же набор имён; `absent` совпадает только с `absent`. Сравнение с текущим состоянием источников выполняет [проверка актуальности](#прикладные-сценарии).

`SourceBaselineError` содержит `code`: `invalid_baseline_source`, `invalid_baseline_state`, `invalid_baseline_digest`, `invalid_baseline_parts`, `invalid_baseline_entry`, `invalid_source_baseline`, `invalid_native_document`. Хешей, имён частей и значений в ошибке нет; при разборе файла черновика любой из них даёт `invalid_draft_baseline`.

## Сохранённый кандидат

`DraftCandidateState` из `keenvpn.domain.draft_candidate_state` хранит собственный неизменяемый JSON-снимок. Раздел `candidate` содержит три обязательных поля:

| Поле | Содержимое |
|---|---|
| `original` | Полный исходный снимок восьми источников; части Xray в лексическом порядке имён |
| `snapshot` | Полный изменённый снимок тех же источников; порядок частей Xray сохраняется |
| `geo_revisions` | Объект с обязательными `geoip` и `geosite`: каждый отображает имя файла в ожидаемый SHA-256; пустой объект допустим |

Каждый снимок — объект со всеми восемью ключами `BaselineSource`. Значение `null` означает засвидетельствованное отсутствие источника, пропущенный ключ недопустим. `xray_configs` — массив пар `[имя, base64]`, до 64 уникальных имён `*.json`; пять файлов XKeen — строки base64. Пустой массив частей и пустая строка файла отличаются от отсутствия. Base64 строгий, с каноническим дополнением, без пробелов; это обратимое кодирование, **не шифрование**. Байты файлов, включая комментарии и оболочку init, сохраняются точно. `keenetic_policies` и `keenetic_hotspot_settings` — полные native-объекты, включая `permit`, неизвестные поля и порядок массивов; ключи объектов при подготовке упорядочиваются как в исходных отпечатках.

Свойства `original` и `snapshot` возвращают независимые полные `DraftDiffSnapshot`, `geo_revisions` — кортеж `GeoDatabase` с видом, именем и ожидаемым хешем. Общая модель и `prepare_snapshot` расположены в `keenvpn.domain.draft_snapshot`; прежний импорт из `keenvpn.application.draft_diff_snapshot` сохранён. `export()` возвращает приватную копию всего раздела для доверенного кода. Эти данные не входят в `DraftView`, `to_diagnostic`, `repr`, ошибки или журналы.

Неизвестные поля раздела, неизвестные записи обоих снимков и неизвестные виды геобаз сохраняются при перекодировании и редактировании. Формат известных записей проверяется строго. `build_draft_candidate` заменяет полные значения известных источников кандидата; вызывающий отвечает за сохранение неизвестных конфигурационных полей внутри переданных полных документов. Исходный снимок при повторном редактировании остаётся прежним. Неизвестные записи не интерпретируются; их сохранение не означает, что известные проверки проверили эти данные. Ожидаемые хеши геобаз не являются свидетельством наличия категорий.

Весь файл сессии, включая оба снимка, base64 и неизвестные данные, ограничен прежним 1 МиБ; при превышении запись отклоняется. Прежние v1 без `candidate` читаются и кодируются без добавления этого поля; миграции при чтении нет. Сохранение не выполняет статическую проверку правил, запуск Xray, diff или применение.

## Файловое хранилище

`DraftSessionFiles(directory, *, protected_directories=PROTECTED_DIRECTORIES)` реализует `DraftSessionStore`. Механика приватного файла общая с [хранилищем метаданных](manager-metadata.md#файловое-хранилище) — модуль `keenvpn.adapters.private_files`:

- `directory` — абсолютный нормализованный путь собственного каталога, например `/tmp/mnt/<UUID>/draft`. Значения по умолчанию нет. Каталог, совпадающий с `/opt/etc/xray`, `/opt/etc/xkeen` или `/opt/etc/init.d` либо вложенный в них, отклоняется до обращения к файловой системе.
- Ни один компонент пути не может быть символической ссылкой. Родитель каталога должен существовать: адаптер не создаёт родителей и не переключается на другой каталог, `/opt` или RAM. Идентичность раздела по UUID и свободное место заранее не проверяются.
- Каталог должен принадлежать текущему пользователю и иметь права `700`, файл `draft-session.json` — обычный файл владельца с правами `600`; права не исправляются.
- `read_draft()` возвращает `None`, если каталога или файла ещё нет, и не берёт блокировку.
- `create_draft(session)` сначала кодирует модель: некорректная вызывает `DraftSessionError` без обращения к файлам. Затем при необходимости создаёт каталог с правами `700`, берёт эксклюзивный неблокирующий `flock` каталога, удаляет временные файлы прерванной записи и требует, чтобы черновика не было: существующий, в том числе с теми же байтами, — `draft_revision_conflict` без перезаписи. Файл публикуется так же, как метаданные: временный файл с правами `600`, fsync, повторная проверка отсутствия черновика и неподменённого каталога, переименование и fsync каталога. Возвращается ревизия.
- `replace_draft(session, expected_revision)` заменяет существующую сессию по полной ревизии SHA-256, не по токену интерфейса. Некорректные входы отклоняются до файловых обращений. Отсутствие собственного каталога или файла и устаревшая ревизия дают `draft_revision_conflict` без создания каталога и записи сессии; повреждённый файл не перезаписывается. Используются та же блокировка, временный файл, проверки ревизии/подмены и fsync, что у создания. Возвращается SHA-256 записанных байтов. При совпадении байтов переименования нет, но выполняется fsync файла и каталога с повторными проверками.
- `remove_draft(expected_revision)` проверяет формат ревизии (неверный — `DraftSessionError` без обращения к файлам), берёт ту же блокировку, открывает файл, сверяет ревизию, проверяет, что путь указывает на удерживаемый файл, удаляет его и выполняет fsync каталога. Отсутствующий черновик и другая ревизия — `draft_revision_conflict`; повреждённый файл не удаляется. Удаляется только файл сессии: собственный каталог и чужие файлы в нём остаются. Файл, появившийся после удаления до проверки, которая следует за fsync каталога, не трогается — `draft_revision_conflict`.
- `confirm_draft_absent()` закрепляет на диске отсутствие черновика, ничего не удаляя: берёт ту же блокировку, проверяет, что файла нет и каталог не подменён, выполняет fsync каталога и повторяет проверки. Нужен повтору отмены после `draft_write_unconfirmed`. Нет собственного каталога — подтверждать нечего, каталог не создаётся. Файл или другой объект по пути черновика, в том числе повреждённый или ссылка, — `draft_revision_conflict` без удаления; отказ fsync — снова `draft_write_unconfirmed`.
- Создание, замена, удаление и подтверждение отсутствия через адаптер исключают друг друга блокировкой. Процесс, который меняет файл в обход блокировки, обнаруживается вплоть до последней проверки перед переименованием или удалением; изменение в промежутке между ней и самой операцией адаптер обнаружить не может: атомарного «сравнить и заменить» или «сравнить и удалить» в POSIX нет. Подмена каталога во время операции даёт `draft_store_unsafe` с причиной `replaced`.

Отказы — `DraftSessionStoreError` с полями `failure` (`DraftStoreFailure`) и `reason` (`StoreReason` или код домена) и фиксированным текстом без путей и системного сообщения:

| `failure` | Когда | `reason` |
|---|---|---|
| `draft_store_unavailable` | Родитель отсутствует, каталог или файл не читается | `missing`, `permission_denied`, `io_error`, `no_space`, `read_only` |
| `draft_store_unsafe` | Недопустимый или защищённый каталог, ссылка, не каталог или не обычный файл, чужой владелец, неверные права, подмена каталога или файла | `invalid_directory`, `protected_directory`, `symlink`, `not_directory`, `not_regular_file`, `owner`, `permissions`, `replaced` |
| `draft_store_busy` | Блокировку держит другая операция | — |
| `draft_revision_conflict` | При создании черновик уже есть; при замене или удалении его нет или ревизия другая; при подтверждении отсутствия по пути черновика что-то есть | — |
| `invalid_stored_draft` | Файл нарушает формат или имеет другую версию схемы | код домена: `invalid_draft_json`, `unsupported_draft_schema_version` и другие |
| `draft_write_failed` | Не удалось создать каталог, записать, закрепить или переименовать временный файл либо удалить файл; прежнее состояние сохранено | `no_space`, `read_only`, `permission_denied`, `io_error` |
| `draft_write_unconfirmed` | Созданный или заменённый файл виден либо удалённый исчез, но fsync каталога не удался, в том числе при подтверждении отсутствия; состояние нужно перечитать | `io_error` |

`KeyboardInterrupt` и `SystemExit` проходят наружу; до переименования или удаления прежнее состояние файла не меняется, а временный файл удаляется. Процесс, убитый между записью и переименованием, оставляет только временный файл, который удаляет следующая операция.

## Прикладные сценарии

Модуль `keenvpn.application.draft_session` содержит четыре сценария над портом `DraftSessionStore`; решение о выходе из меню (`InspectMenuExit`) — в модуле `keenvpn.application.menu_exit` над тем же портом с общим [контрактом результата](application.md#результат); коды отказов и следующие шаги — в [описании прикладных сценариев](application.md#сессия-черновика).

- `InspectDraft` — `InspectDraftHandler(store)` один раз читает черновик. `data` — `DraftStatusView(present, draft)`; без черновика `present=False`, это состояние, а не отказ.
- `CreateDraft` — `CreateDraftHandler(store, fingerprints, *, draft_ids=new_draft_id, clock=utc_now)` один раз читает хранилище; существующий черновик — отказ `draft_exists` без чтения источников и без записи. Затем по одному разу читает отпечаток каждого источника перечня через порт `SourceFingerprintSource`. Первый недоступный источник останавливает чтение: отказ `draft_baseline_unavailable` с кодом отказа чтения в `reason`, файл не создаётся. Некорректный отпечаток или отпечаток другого источника — `invalid_draft_baseline_source`. Иначе создаёт сессию с новым UUID, временем `clock()` в UTC без долей секунды и разделом `baseline`; ревизия, которую вернуло хранилище, должна совпасть с SHA-256 канонических байтов, иначе — `invalid_draft_store_result`. `data` — `DraftView`.
- `DiscardDraft(draft_id=..., expected_revision=...)` — идентификатор и токен ревизии из `DraftView`; неверный формат любого из них — `invalid_command` без чтения хранилища. `DiscardDraftHandler(store)` один раз читает хранилище. Нет черновика — хранилище закрепляет его отсутствие (`confirm_draft_absent`), затем `DraftDiscardView(outcome="already_absent")`: повтор после `draft_write_unconfirmed` не сообщает успех, пока удаление не закреплено на диске, а отказ подтверждения возвращается как отказ хранилища. Другой идентификатор — отказ `draft_mismatch`, другой токен — `draft_revision_conflict`, оба без удаления; совпадающий удаляется по прочитанной ревизии — `outcome="discarded"`.
- `CheckDraftBaseline(draft_id=..., expected_revision=...)` — те же поля, что у отмены. `CheckDraftBaselineHandler(store, fingerprints)` проверяет, не устарел ли черновик, и ничего не записывает. Нет черновика, другой идентификатор или токен — те же конфликты черновика, что у отмены, источники при этом не читаются. Иначе сценарий по одному разу читает отпечаток каждого источника перечня, в том числе не зафиксированного в черновике, и сравнивает с исходным; отказ одного источника не останавливает чтение остальных. Затем черновик читается повторно: изменившийся или исчезнувший за время проверки — `draft_revision_conflict`. Изменившийся, исчезнувший или появившийся источник, источник без записи в черновике, черновик без раздела `baseline` или с неизвестными записями — отказ `draft_baseline_changed` с записью конфликта по каждому такому источнику и шагом «создать черновик заново». Источник, который прочитать не удалось, совпадением не считается: если других расхождений нет, отказ несёт код и причину первого отказа чтения. Успех — `DraftBaselineCheckView(outcome="current", draft_id)`. Ту же проверку выполняет общий помощник `check_draft_current`; при успехе он возвращает прочитанный черновик с ревизией из чтения. Проверка — снимок на момент чтения: изменение после её завершения она не обнаруживает.

`DraftView` содержит `draft_id`, `revision` — непрозрачный токен ревизии, `created_at` строкой, `unknown_field_count` и `baseline` — `DraftBaselineView` с источниками и их состояниями (`BaselineSourceView(source, state)`) и числом неизвестных записей либо `None`, если раздела в файле нет. Путь, ревизия файла, хеши, имена частей, имена и значения неизвестных полей в результаты не входят. Отказ создания, замены или удаления, в том числе `draft_write_unconfirmed`, не превращается в успех.

Токен ревизии — первые 128 бит SHA-256 от метки домена и ревизии файла, 32 шестнадцатеричные цифры в нижнем регистре (`draft_revision_token`). Любое изменение байтов файла, в том числе внешняя правка, меняет токен, поэтому команда с токеном устаревшего представления отклоняется конфликтом и ничего не изменяет. Токен не совпадает ни с ревизией файла, ни с хешами источников и не позволяет их получить. Отказы `draft_exists`, `draft_mismatch` и `draft_revision_conflict` при создании, редактировании, удалении и проверке актуальности несут [запись конфликта](application.md#конфликт-ревизий) черновика без токенов и ревизий.

## Редактирование сохранённого кандидата

`UpdateDraftHandler(store)` из `keenvpn.application.draft_update` принимает `UpdateDraft(draft_id=..., expected_revision=..., candidate=..., original=None, geo_revisions=None)`, машинное имя `update_draft`, версия контракта 1. `candidate` — полный `DraftDiffSnapshot`. При первом редактировании обязателен полный `original`; при следующих его можно опустить. `geo_revisions=None` сохраняет прежние ожидания, а при первом редактировании означает пустой набор; явный пустой кортеж очищает известные ожидания. Неизвестные виды геобаз сохраняются.

Сначала проверяются команда, версия, идентификатор и токен, затем читается сессия общим `read_expected_draft`. Чужой `draft_id` даёт `draft_mismatch`, устаревший токен или отсутствующая сессия — `draft_revision_conflict` с записью конфликта. Повреждённый файл не перезаписывается. Затем формируется собственный неизменяемый раздел кандидата. Некорректные снимки, ревизии геобаз и попытка заменить уже сохранённый original дают `invalid_draft_candidate`; сравнение original различает JSON-типы, в том числе `true`, `1` и `1.0`.

С уже записанным `baseline` сверяется именно исходный снимок из подготовленного раздела, который попадёт в файл. Источники на роутере не читаются, отпечатки сессии не пересчитываются. Неполный/неизвестный baseline или несовпадение подготовленного original с ним дают `draft_original_mismatch`; старую сессию без полного baseline можно читать, но редактировать этим сценарием нельзя. При первом сохранении другой допустимый original даёт `draft_original_mismatch`; при повторном попытка сменить сохранённый original отклоняется раньше, как `invalid_draft_candidate`. Превышение размера сессии также даёт `invalid_draft_candidate`. Оба кода имеют категорию `invalid_source_data` и шаг `inspect_source_data`.

Сценарий сохраняет идентификатор, время создания, baseline и неизвестные поля сессии, заменяет только раздел кандидата. В `replace_draft` передаётся полная ревизия из чтения. Хранилище повторно сверяет её под блокировкой, поэтому правка после чтения также отклоняется. Успех возвращает прежний безопасный `DraftView` с токеном новых байтов; неизменный кандидат после подтверждения fsync возвращает тот же токен. Неверная ревизия в ответе хранилища — `invalid_draft_store_result`.

При `draft_write_unconfirmed` новые байты уже могут быть видны: нужно перечитать сессию и повторять с актуальным токеном. Сохранение кандидата не удостоверяет актуальность живых источников, пригодность Xray или применение. В меню этот сценарий не подключён; адаптеры чтения роутера отклоняют и новый метод замены с `read_only`.

## Предварительная проверка кандидата

`CheckDraftCandidateHandler` из `keenvpn.application.draft_candidate` принимает команду
`CheckDraftCandidate(draft_id=..., expected_revision=..., candidate=...)`.
Вызывающий формирует `DraftCandidate` из полного набора частей Xray, параметров init XKeen,
списков `port_exclude.lst` и `port_proxying.lst`. Для каждой используемой геобазы
`geo_revisions` содержит `GeoDatabase` с типом, именем файла и ожидаемым SHA-256.
Исходные документы, служебные правила и неизвестные поля сохраняют переданные байты.
При проверке значение `null` эквивалентно пропуску необязательных полей `dns.tag`,
`dns.hosts`, `dns.servers`, а также `tag`, `domains`, `expectIPs`, `expectedIPs`
и `unexpectedIPs` объекта DNS-сервера. В объекте правила пропускаются известные
поля условий, тегов и типа с точным именем и значением `null`. У outbound
пропускается `tag: null`. Правило, оставшееся без условий, даёт ошибку схемы.
Неизвестный ключ или вариант регистра сохраняется при анализе и ограничивает проверку.
У действующего раздела маршрутизации поле `domainStrategy` допускает строку,
`null` или отсутствие. В правилах поле `type` декодер Xray 26.3.27 игнорирует.

Обработчик получает хранилище сессии и источник отпечатков. При наличии ссылок на геобазы
он использует переданный источник инвентаря и кортеж доверенных `GeoCategoryCatalog`.
Каталог содержит тип базы, имя файла, SHA-256 и полный набор кодов категорий в верхнем регистре.
Пустой набор означает, что в базе нет категорий, а `categories=None` обозначает подтверждённое повреждение.
Сценарий работает с этими сведениями в памяти. Он не разбирает бинарные базы.

| Проверка | Что можно установить |
| --- | --- |
| `candidate_schema` | Структуру поддерживаемых разделов и правил, обязательные типы и пустые условия. Неизвестный протокол ограничивает проверку. |
| `candidate_targets` | Наличие и однозначность целей, включая действующий обработчик API, inbound и теги DNS. Импорт разрешает outbound после объединения частей и проверяет селекторы и резервные цели всех объявленных балансировщиков. Варианты регистра, которые модель не интерпретирует однозначно, дают неполный итог. |
| `candidate_rule_order` | Положение финального правила и статические пересечения условий. Предупреждения содержат позиции правил с нуля. Полное покрытие и частичное пересечение домена или сети различаются. Код `earlier_geo_rule` означает возможное влияние раннего геоправила. Проверка сохраняет различие между GeoIP RU и доменными зонами. Домены сравниваются в канонической форме модели, в том числе IDNA. |
| `candidate_geo_categories` | Для ссылок действующих разделов маршрутизации и DNS проверяются наличие файла, ожидаемая ревизия и наличие категории в каталоге той же базы. Отсутствующие файл или категория, повреждение и смена ревизии дают ошибку. Без свидетельства о категории или ожидаемой ревизии результат неполон. Достоверное сравнение кодов категорий ограничено ASCII. |
| `dns_port_53_mode_consistent` | Общее с быстрой проверкой правило сверяет оба списка, `proxy_dns` и `proxy_router`. Отсутствие исключения допустимо. [Режим порта 53](quick-check.md) |

Каждый элемент `checks.items` содержит стабильные поля `code`, `status` и `reason`.
У пройденной проверки `reason` равен `null`. Одна проверка возвращает одну причину,
остальные проверки сохраняют собственные результаты.

| Проверка | Статус | Причина и значение |
| --- | --- | --- |
| Схема | `failed` | `invalid_reference_structure` — неверен тип `routing.domainStrategy` либо структура прочитанных полей inbound, DNS, API или ссылок inbound. `outbound_protocol_invalid` — в действующем outbound отсутствует непустая строка протокола. |
| Схема | `failed` | `routing_unsupported`, `rules_unsupported`, `rule_not_object`, `values_invalid`, `values_empty`, `rule_without_conditions`, `outbounds_unsupported`, `balancers_unsupported` — нарушение структуры или отсутствие обязательных данных. |
| Схема | `unsupported` | `routing_missing` — нет раздела маршрутизации. `outbound_chained`, `outbound_protocol_unsupported`, `balancer_mixed`, `fallback_mixed` — статическая модель не определяет единое действие объявления. |
| Цели | `failed` | `duplicate_inbound` — повтор тега inbound сохраняется после объединения частей. `missing_inbound` — ни inbound, ни действующий тег DNS не разрешает ссылку. |
| Цели | `failed` | `target_invalid`, `target_missing`, `target_ambiguous`, `target_duplicate`, `target_unresolved`, `fallback_unresolved`, `balancer_invalid`, `balancer_empty` — причины разрешения из [модели импорта](routing-import.md#назначение-и-действие). |
| Цели или геобазы | `not_checked` | `schema_incomplete` — структура входа ограничивает зависимую проверку. |
| Порядок | `failed` | `catch_all_not_last` — правило для всего трафика TCP/UDP расположено до конца списка. |
| Порядок | `unsupported` | Первая причина группы, значения или отсутствующей политики из [модели импорта](routing-import.md). |
| Порядок | `not_checked` | `comparison_limit` — исчерпан бюджет попарных сравнений. |
| Схема, цели, порядок или геобазы | `unsupported` | `field_case_variant` — неоднозначный регистр ключа препятствует интерпретации. |
| Геобазы | `failed` | `invalid_geo_reference` — некорректная ссылка. `missing_geo_file` — источник подтвердил отсутствие файла. `corrupt_geo_file` — нулевой размер либо каталог подтвердил повреждение. |
| Геобазы | `failed` | `geo_revision_changed` — текущий SHA-256 отличается от ожидаемого. `geo_category_missing` — в подтверждённом каталоге нужной ревизии нет категории. |
| Геобазы | `not_checked` | `source_not_connected` — источник инвентаря не передан. `geo_databases_unavailable` или `invalid_geo_databases` — отказ источника или некорректный ответ. `file_not_inventoried` — инвентарь не содержит сведений об этом файле. |
| Геобазы | `not_checked` | `geo_revision_unknown` — нет ожидаемой ревизии. `geo_categories_unverified` — нет достоверного каталога для типа, файла и хеша. `candidate_references_incomplete` — код категории содержит символы за пределами ASCII. `no_references` — в действующих разделах нет ссылок на геобазы. |
| Порт 53 | `failed` | `port_53_in_both_lists`, `exclude_list_ignored`, `proxy_dns_contradicts_exclusion` — конфликт списков или режима DNS. |
| Порт 53 | `unsupported` | `flags_unknown` — состояние `proxy_dns` или `proxy_router` нельзя прочитать однозначно. |

Перед возвратом отчёта `check_draft_current` сверяет сессию и исходные отпечатки. Конфликт
или отказ чтения возвращается в `Result.error` с кодом и следующим шагом. Успешное выполнение
возвращает `data.checks`, `warnings`, `next_step` и один из трёх исходов.

- `failed` — хотя бы одна проверка обнаружила нарушение.
- `incomplete` — обязательную проверку выполнить полностью не удалось. Например, отсутствуют сведения
  о категориях или исчерпан лимит в 50 000 сравнений условий. Уже найденные предупреждения сохраняются.
- `passed` — все применимые статические проверки пройдены. При отсутствии геоссылок
  проверка категорий помечается `not_checked / no_references` и пропускается при подсчёте итога.

При ошибке следующий шаг определяется первой неуспешной проверкой. Ошибка в черновике
даёт `review_draft`, отсутствующий или повреждённый файл геобазы — `check_source`,
изменение ожидаемой ревизии базы — `open_view`. При неполном результате отсутствие
ожидаемого хеша в кандидате (`geo_revision_unknown`) даёт `review_draft`. Недостающие
сведения инвентаря о базе (`file_not_inventoried`) дают `check_source`. Отсутствие
достоверного каталога категорий (`geo_categories_unverified`), ограничение модели
или лимит сравнений дают `consult_documentation`: повторное чтение файлов
само по себе не подтверждает категории. Если у проверяемых геоссылок несколько причин неполноты, выбирается первая из фиксированного перечня
`file_not_inventoried`, `geo_categories_unverified`, `geo_revision_unknown`, `candidate_references_incomplete`,
`schema_incomplete`. Перестановка ссылок сохраняет причину и следующий шаг. Подтверждённая ошибка
имеет приоритет над неполнотой. При `passed` поле `next_step` пусто.

Отчёт относится к состоянию на момент чтения. Он не блокирует источники и не разрешает запись.
Загрузку конфигурации установленным Xray, прохождение трафика, DNS и работу Pritunl он не проверяет.

## Сравнение двух снимков

`CompareDraftHandler(store, fingerprints).execute(CompareDraft(...))` возвращает отчёт версии 1 для просмотра.
Команда принимает `draft_id`, `expected_revision` и два полных `DraftDiffSnapshot` в полях `original` и `candidate`.
Классы команды и снимка доступны из `keenvpn.application.draft_diff`. Вызывающий передаёт все восемь полей
каждого снимка по имени. Для подтверждённо отсутствующего источника передаётся `None`.
Пустой каталог и пустой файл считаются присутствующими.

| Поле снимка | Содержимое в памяти |
| --- | --- |
| `xray_configs` | `XrayConfigSet` с исходными байтами каждой части JSON |
| `xkeen_settings`, `xkeen_init` | Байты файла настроек JSON и скрипта init |
| `xkeen_port_exclude`, `xkeen_port_proxying`, `xkeen_ip_exclude` | Байты UTF-8 каждого списка XKeen |
| `keenetic_policies` | Полный объект JSON ресурса `ip/policy`, включая `permit` и дополнительные поля |
| `keenetic_hotspot_settings` | `KeeneticHotspotSettings` с полным объектом `ip/hotspot` |

Полные снимки предоставляет вызывающий код. Для `xkeen_init` нужны исходные байты файла,
а `XKeenInitSource` возвращает только разобранные присваивания в `XKeenInitParameters`.
Для `keenetic_policies` нужен весь объект `ip/policy`, включая `permit` и дополнительные поля.
Штатный `KeeneticPolicySource` возвращает `KeeneticPolicySet` с ID и описаниями политик.
У `original` части Xray должны идти в лексическом порядке имён, как при чтении каталога. Другой порядок даёт `invalid_diff_snapshot`.
У `candidate` порядок загрузки задаёт переданный `XrayConfigSet`. Если он отличается от лексического,
в отчёте появляется запись `part / reordered` без номеров, в том числе при одновременных изменениях содержимого или состава.
Обработчик сверяет отпечатки переданного `original` с разделом `baseline` ожидаемой сессии. После сравнения снимков он
проверяет текущие отпечатки через порт и повторно читает сессию. Результат относится к моменту
этих чтений. Проверку схемы, ссылок, геобаз и DNS выполняет отдельная команда `CheckDraftCandidate`.

Успех содержит `entries`. Пустой список означает полное совпадение. Каждая запись содержит
код источника `source`, область `area`, операцию `added`, `removed`, `changed` или `reordered`
и две необязательные позиции с нуля. **Операция определяет сторону обеих позиций.** У `removed`
это исходный снимок, у `added`, `changed` и `reordered` — кандидат. Это правило действует и
при удалении вложенного поля, если часть или запись сместились из-за соседней вставки.

`part` — порядковый номер части Xray среди имён файлов либо политики Keenetic среди ID политик.
`position` — индекс элемента внешнего сравниваемого массива. Например, для учётных данных внутри
`servers` или `accounts` это номер outbound или inbound, для правила — номер в `routing.rules`,
для записи политики — номер элемента в `permit`. У перестановки массива целиком нет номера
элемента этого массива. Неприменимые координаты равны `null`.

| Коды области `area` | Что изменилось |
| --- | --- |
| `source`, `part` | Присутствие целого источника или отдельной части Xray, порядок загрузки частей кандидата |
| `file`, `representation` | Содержимое скрипта init либо байтовое представление при одинаковой разобранной структуре JSON или списка |
| `field_order`, `other_fields` | Порядок полей объекта либо содержимое дополнительных полей, сгруппированных без вывода их имён |
| `routing`, `routing_rules`, `balancers`, `domain_strategy` | Раздел маршрутизации Xray, правила, балансировщики и стратегия разрешения доменов |
| `inbounds`, `outbounds`, `connection`, `connection_settings` | Входящие и исходящие подключения, их тег или протокол, параметры подключения |
| `servers`, `accounts`, `endpoint`, `credentials` | Серверы и учётные записи, адрес или порт, распознанное поле учётных данных. Значения приватны |
| `transport`, `reality`, `tls` | Параметры транспорта, REALITY или TLS |
| `api`, `dns`, `log`, `observatory` | Разделы API, DNS, журналирования и наблюдения Xray |
| `xkeen_flags`, `killswitch` | Раздел настроек XKeen и распознанное поле kill-switch |
| `start_auto`, `proxy_dns`, `proxy_router`, `ipv6_support` | Одноимённые параметры init XKeen |
| `list_entries` | Записи одного из трёх списков XKeen, указанных в `source` |
| `policy`, `permit`, `description` | Политика Keenetic, её упорядоченный список разрешённых подключений, описание |
| `hosts`, `segment_assignments`, `auto_register` | Записи устройств, назначения сегментов и параметр автоматической регистрации hotspot |

Например, `routing_rules / reordered` означает перестановку правил, `credentials / changed` —
изменение учётных данных в распознанном поле подключения. Произвольные имена, значения, пути,
размеры и хеши остаются в приватном входе.

- Части Xray сопоставляются по имени внутри сравнения. Переименование отражается удалением и добавлением.
- При различии только в оформлении JSON, комментариях или оформлении строк списка возвращается
  `representation / changed`. При изменении структуры видны затронутые области. Явный `null`
  отличается от пропущенного поля. Порядок ключей JSON файлов учитывается отдельно от оформления,
  поскольку Xray может прочитать несколько вариантов регистра одного ключа.
- В init флаги `start_auto`, `proxy_dns`, `proxy_router` и `ipv6_support` имеют отдельные области.
  При переключении распознанного значения выводится имя флага. Иные изменённые байты дают также
  `file / changed`. Для нечитаемого скрипта доступен общий факт изменения файла. В настройках JSON
  изменение поля `xkeen.killswitch` выделяется областью `killswitch`.
- В объектах native порядок ключей не влияет на результат. Порядок массивов значим. Изменения
  неизвестных полей одного объекта группируются в закрытую область. Отчёт не содержит значений для записи.

При неполном или повреждённом входном снимке возвращается `invalid_diff_snapshot`. Если `original`
расходится с `baseline` сессии, обработчик сверяет текущие источники и ревизию сессии.
Если они актуальны, возвращается `diff_original_mismatch` с шагом `inspect_source_data`.
Если текущий источник изменился, возвращается `draft_baseline_changed` с записью конфликта и шагом
`recreate_draft`. Это относится и к случаю, когда вызывающий код собрал `original` повторным чтением.
При неполном или неизвестном составе `baseline`, смене ревизии и отказе чтения действуют общие ошибки сверки.
Если операций больше 256, возвращается `diff_entry_limit`. Каждый такой отказ содержит следующий шаг,
поле `data` равно `null`.

## Пример

```python
import os
import tempfile

from keenvpn.adapters.draft_session_files import DraftSessionFiles
from keenvpn.adapters.router_sources import SourceFingerprints
from keenvpn.application.draft_session import (
    CheckDraftBaseline, CheckDraftBaselineHandler, CreateDraft, CreateDraftHandler, DiscardDraft, DiscardDraftHandler,
    InspectDraft, InspectDraftHandler,
)

store = DraftSessionFiles(os.path.realpath(tempfile.mkdtemp()) + "/draft")
# Пустой временный корень вместо роутера и подставной RCI: файлы источников отсутствуют.
root = os.path.realpath(tempfile.mkdtemp())
fingerprints = SourceFingerprints(root=root, read=lambda resource: {})
created = CreateDraftHandler(store, fingerprints).execute(CreateDraft())
discard = DiscardDraft(draft_id=created.data.draft_id, expected_revision=created.data.revision)
assert [item.state for item in created.data.baseline.sources] == ["absent"] * 6 + ["present"] * 2
assert CreateDraftHandler(store, fingerprints).execute(CreateDraft()).error.code == "draft_exists"
check = CheckDraftBaseline(draft_id=created.data.draft_id, expected_revision=created.data.revision)
assert CheckDraftBaselineHandler(store, fingerprints).execute(check).data.outcome == "current"
# Внешнее изменение: появился список исключений портов XKeen.
os.makedirs(root + "/opt/etc/xkeen")
open(root + "/opt/etc/xkeen/port_exclude.lst", "wb").close()
stale = CheckDraftBaselineHandler(store, fingerprints).execute(check).error
assert (stale.code, stale.next_step.code.value) == ("draft_baseline_changed", "recreate_draft")
assert [item.to_dict() for item in stale.conflicts] == [
    {"subject": "source", "source": "xkeen_port_exclude", "expected": "absent", "found": "present"},
]
assert InspectDraftHandler(store).execute(InspectDraft()).data.draft.revision == created.data.revision
stale = DiscardDraft(draft_id=created.data.draft_id, expected_revision="0" * 32)
assert DiscardDraftHandler(store).execute(stale).error.code == "draft_revision_conflict"
assert DiscardDraftHandler(store).execute(discard).data.outcome == "discarded"
assert DiscardDraftHandler(store).execute(discard).data.outcome == "already_absent"
print(InspectDraftHandler(store).execute(InspectDraft()).data.to_dict())
```

Пример читает и пишет только во временных каталогах, к роутеру и сети не обращается и печатает `{'present': False, 'draft': None}`.

## Проверка установленным Xray

`CheckInstalledXrayHandler(store, fingerprints, tester).execute(CheckInstalledXray(...))` — команда `check_installed_xray` контракта v1. Вызывающий передаёт ID черновика, токен ожидаемой ревизии, полный `XrayConfigSet` в исходном порядке и кортеж `CandidateAsset(kind, name, sha256, content)`. Ожидаемый SHA-256 каждого файла поступает из доверенного источника. Сессия хранит исходные отпечатки. Байты кандидата и его ресурсов передаются отдельно при каждом вызове.

Сценарий сверяет действующие ссылки routing и DNS. Для полного результата в самом кандидате нужны ссылки на категории **обоих** файлов `geoip.dat` и `geosite.dat`. Для дополнительных поддерживаемых ссылок `ext:`, `ext-ip:`, `ext-domain:` требуется соответствующий кандидатный файл с тем же видом и именем. Коды категорий должны быть в ASCII. Остальные коды дают неполную проверку. Список ресурсов должен в точности покрывать зависимости. Содержимое файлов сверяется с SHA-256. Допускается до 64 частей по 1 МиБ, всего до 8 МиБ, и до 32 ресурсов по 256 МиБ, всего до 512 МиБ. До разбора всех частей действует общий бюджет 16 384 разделителей JSON и списков. В счёт входят запятые (включая `\u002c` и `\u002C`), двоеточия и открывающие скобки, в том числе внутри строк и комментариев. Превышение бюджета даёт `invalid_command`.

`StagedXrayTest(directory, runner)` использует существующий каталог владельца с правами 0700. Путь должен быть абсолютным, без символических ссылок и вне защищённых каталогов конфигурации и init. До создания файлов исполнитель подтверждает исключительное владение рабочим пространством до конца очистки, включая защиту от сторонних записей с тем же UID. Одних прав 0700 для этой гарантии недостаточно. Адаптер размещает отдельный временный каталог с подкаталогами `parts` и `assets`. Входные файлы имеют права 0600. Части сохраняются побайтно. Порядок задают повторяющиеся аргументы `-c`, служебные имена сохраняют признак `tail` исходного имени.

Координатор проверки, ядро ОС и администратор хоста с полными полномочиями входят в доверенную часть системы. Контракт изолирует проверочный Xray, его потомков и процессы без административных полномочий, включая процессы с тем же UID. Защита от намеренного вмешательства администратора хоста в этот контракт не входит.

Предел памяти относится к сумме резидентных пользовательских страниц проверочного Xray и его потомков. Общее адресное пространство потоков учитывается один раз. Доверенный координатор, подготовка временных файлов и неотображённый в эти процессы файловый кэш ОС находятся вне этого предела. Резидентные файловые страницы, отображённые в Xray или его потомков, учитываются в памяти соответствующих процессов. Размер зарезервированного виртуального адресного пространства не равен этой метрике.

`IsolatedXrayRunner` — обязательная зависимость исполнения. Он должен проверить доверенный установленный бинарник версии 26.3.27 до запуска, сформировать отдельный неизменяемый cwd из манифеста закреплённых дескрипторов, сверить размер и SHA-256 каждого файла в этом пространстве, открыть входы ядру только для чтения и запретить доступ к другим конфигурациям, базам, файлам и сети. Запрос содержит argv для `run -test -format json`, полный набор переменных окружения из одного `XRAY_LOCATION_ASSET=assets`, срок 30 секунд и общий предел stdout/stderr 64 КиБ и жёсткую границу 256 МиБ памяти на всю группу. Если такие ограничения недоступны, исполнитель обязан отказаться до запуска. Адаптер назначает идентификатор исполнения до запуска. Даже при частичном старте или некорректном ответе он требует завершить группу по этому идентификатору и дождаться потомков. Сбой завершения имеет приоритет перед изменением временных файлов. До запуска и после завершения группы адаптер перечитывает содержимое через закреплённые дескрипторы, сверяет хеши и записи каталогов, затем удаляет собственные временные объекты. При отказе очистки проверка завершается ошибкой. Объект, принадлежность которого невозможно установить после подмены или ошибки файловой системы, может остаться в приватном каталоге. Штатный режим меню не подключает исполнителя. Локальные тесты проверяют этот протокол управляемым двойником.

Сессия и исходные отпечатки сверяются перед подготовкой и после исполнения. Общий конфликт черновика имеет приоритет при выдаче результата. Без конфликта команда возвращает `CheckView` с кодом `installed_xray_candidate` и `network=false`.

| Статус проверки | Причина и действие вызывающего |
| --- | --- |
| `passed` | Исполнитель подтвердил config test. Результат относится к переданным байтам и моменту сверки. Перед записью требуется собственная сверка под блокировкой. |
| `not_checked` | `both_geo_references_required` или `candidate_references_incomplete`. Проверьте, какие категории использует сам кандидат. |
| `failed` | `candidate_assets_mismatch`, `candidate_asset_size` или `candidate_asset_digest` требуют сверки ресурсов. `xray_candidate_rejected` означает отказ ядра при загрузке. Сырые потоки и подробности конфигурации скрыты. |
| `unsupported` | `xray_version_unsupported`. Исполнитель не подтвердил поддерживаемую версию. |

Части с настройками `log` передаются в исходном виде. Если во время config test изоляция запретила файловую операцию, например открытие файла журнала, исполнитель сообщает об этом отдельно от stdout/stderr и кода выхода. Команда проверяет типы ответа и общий лимит вывода. В пределах лимита подтверждённый запрет даёт `xray_test_unavailable` с причиной `xray_file_access_denied` независимо от кодировки потоков и кода выхода. Исполнитель без такого наблюдения должен сообщить `xray_isolation_unavailable`. Для успеха требуются код выхода 0, баннер ожидаемой версии и отдельная строка `Configuration OK.`. После неё допускаются сообщения консольного журнала в пределах лимита.

Неверная форма команды или версия контракта даёт общий `ErrorDetail`. При сбое исполнения возвращается `xray_test_unavailable` с закрытой причиной и следующим шагом `check_source`. Причины различают отсутствие бинарника, недоступную изоляцию, сбой запуска, таймаут, превышение или некорректность вывода, прерывание, сбой подготовки, подмену, ошибку очистки и ответ вне контракта. Проверка не применяет файлы и не подтверждает доступность VPN.

### Изолированный Linux-исполнитель

`IsolatedInstalledXray` из `keenvpn.adapters.xray_isolated_port` реализует порт `tester` для `CheckInstalledXrayHandler`. Импорт модуля и создание объекта не запускают процессы. Исполнение начинается при вызове `test`; `vpn-menu --read-router` подключает этот порт к пункту 7 → 2. При недоступных Python-зависимостях порт не подключается, остальные функции меню сохраняются. Необязательный аргумент конструктора `memory_limit` задаётся в байтах и позволяет уменьшить предел с исходных 256 МиБ, например `IsolatedInstalledXray(memory_limit=128 * 1024 * 1024)`. Такое же ограничение принимает `StagedXrayTest`. Значение должно быть положительным целым числом не больше 256 МиБ; иной ввод даёт отказ до файлов и запуска.

Порт допускает только native Linux AArch64 с ядром `4.9-ndm-5`, страницей 4096 байт и 64-битным ABI. Вызывающий процесс должен работать от root, быть однопоточным и иметь необходимые полномочия для mount namespace, chroot, смены идентичности, ptrace и завершения собственного ребёнка, а также `CAP_SYS_RESOURCE` для чтения лимитов процесса другого UID. Полномочия проверяются в действующем наборе (effective). Обработчики сигналов и способ ожидания детей также проверяются до запуска. Выделенный координатор подтверждает отсутствие посторонних детей через `waitid` с `WNOWAIT` и `__WALL`, не забирая их статусы; отсутствие готового события не считается подтверждением пустоты. Установленный `/opt/sbin/xray` должен быть обычным файлом root без символических ссылок и записи для группы или остальных пользователей. Размер и SHA-256 должны совпасть с закреплённым в коде официальным ELF Xray 26.3.27 для Linux arm64. Несовпадение не разрешает запуск другого бинарника.

Отдельный доверенный процесс сначала создаёт private mount namespace и подтверждает отсутствие распространения mount-операций на хост. Временные файлы появляются только после этого, на собственных tmpfs. Проверочный процесс получает chroot с копиями файлов манифеста и исполняемым ELF. Область переводится в режим только чтения; ELF доступен этому процессу на исполнение, но не на чтение. Перед exec сбрасываются UID/GID до 65534, дополнительные группы и активные capabilities, включаются `no_new_privs` и защита от дампа. Родитель проверяет состояние после exec до возобновления пользовательских инструкций. При входе в Xray открыты только три собственных канала: stdin с немедленным EOF и stdout/stderr для ограниченного вывода. Все пишущие концы stdin закрыты до fork; пользовательский ввод и `/dev/null` процессу не передаются.

Все системные вызовы проверочного процесса проходят через ptrace. Закрытый профиль допускает чтение в chroot, внутренние операции Go и получение сведений об ОС через `uname`, запрещает сеть, повторный exec, изменение файлов и создание отдельного адресного пространства. Изменение имени хоста или домена не разрешено. Потоки разрешены только с проверенным набором флагов и общими счётчиками. Отказ файловой операции учитывается отдельно от вывода Xray. Незнакомый syscall или непроверенное состояние останавливает исполнение.

За одно задание разрешается до 63 вызовов создания потоков помимо исходного потока; отказ создания и завершение потока не возвращают этот бюджет. Координатор учитывает завершение ребёнка до получения события clone, в том числе после завершения родительского потока. Живой ребёнок остаётся остановленным до подтверждения принадлежности группе и защитных свойств. Позднее событие для уже забранного ребёнка не вызывает операций над его освобождённым TID; неоднозначное повторное использование номера даёт отказ изоляции.

Предел 256 МиБ обеспечивается консервативным предварительным учётом потенциально резидентных страниц. До exec резервируются ELF, весь разрешённый стек и служебные отображения ядра; перед разрешением memory-syscall учитывается возможный рост. Освобождение памяти не возвращает бюджет. Поэтому проверка может завершиться отказом раньше, чем фактический RSS достигнет 256 МиБ; ограничение виртуального адресного пространства вместо RSS не применяется.

Подготовка имеет отдельное ограничение: сумма размеров двух tmpfs не должна превышать 128 МиБ. Она включает две копии входов, пофайловое округление до страницы, копию ELF и два резерва каталогов по 512 КиБ. Более крупный вход отклоняется до создания файлов с `xray_isolation_unavailable`, даже если проходит общую проверку размеров команды. Этот предел подготовки не входит в 256 МиБ памяти Xray.

Основной срок исполнения — 30 секунд с начала вызова порта, включая подготовку. Общий вывод ограничен 64 КиБ; запрошенные записи в stdout/stderr учитываются до выполнения syscall. После результата, таймаута или отмены выполняется отдельная ограниченная очистка с ожиданием собственных процессов, закрытием дескрипторов и обычным размонтированием tmpfs. Повторная отмена не прерывает уже начатое завершение координатора и удаление временных файлов: при подтверждённой очистке сохраняется исходный таймаут или прерывание. Отмена, замеченная после успешного исполнения, меняет успех на прерывание. Неподтверждённая очистка имеет приоритет над обычным результатом. Между доверенными процессами передаётся только закрытый код результата; сырые stdout/stderr Xray не выходят через порт.

Локальные тесты проверяют расчёт бюджета, профиль syscall, подготовку файлов, протокол ptrace и отказы очистки через управляемые двойники ОС. Их прохождение само по себе не подтверждает выполнение нативных операций на оборудовании.
